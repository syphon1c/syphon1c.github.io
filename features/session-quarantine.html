Session Quarantine (Kill Switch) ​

The AI Security Gateway includes a session quarantine feature that provides a surgical "kill switch" for blocking individual user sessions without stopping the entire proxy. This is a core control within the AWARE Framework (R — Real-Time Risk Scoring & Blocking) for immediate threat containment.

Overview ​

The Session Quarantine system provides:

  • Surgical Session Blocking: Block a specific user, API key, or IP address without disrupting other users on the same proxy
  • Immediate Enforcement: Quarantined sessions are rejected at the earliest point in the proxy pipeline — before any content analysis, tool execution, or upstream forwarding occurs
  • Time-Based Expiry: Optionally set a TTL so quarantine entries auto-expire after a defined period
  • Accumulated Risk Auto-Quarantine: Sessions that accumulate excessive risk across multiple requests are automatically quarantined
  • Full Audit Trail: Every quarantine and release action is logged for compliance and investigation
  • Cross-Transport Coverage: Enforced across HTTP, WebSocket, and SSE connections for both MCP and LLM proxies

Understanding the Threat ​

Why is session-level blocking needed?

Traditional proxy controls are binary — the proxy is either running (all users can connect) or stopped (no users can connect). This creates a gap when:

  1. A single user is exhibiting suspicious behavior (prompt injection, data exfiltration attempts)
  2. An API key has been compromised and is being used for unauthorized access
  3. An automated agent is drifting outside its intended scope and needs to be contained
  4. A security alert requires immediate containment while investigation continues

Session Quarantine fills this gap by allowing targeted blocking of individual sessions while keeping the proxy operational for all other users.

Accessing Session Quarantine ​

From the Proxy Management Page ​

  1. Navigate to Proxies in the main menu
  2. Find the proxy you want to manage
  3. Click the "Quarantine" button in the proxy's action row

This opens the Session Quarantine management modal for that proxy.

Session Identification ​

The quarantine system identifies sessions using a priority-based approach:

PriorityIdentifier TypeExampleWhen Used
1 (Highest)OAuth User Identityuser@example.comWhen the request comes from an authenticated OAuth session
2API Keyapikey:42When the request uses an API key
3 (Fallback)Client IP Address192.168.1.100:54321When no authentication context is available

When quarantining a session, you provide the session identifier that matches how the user authenticates to the proxy.

Quarantining a Session ​

Step 1: Open the Quarantine Manager ​

Click the "Quarantine" button on any proxy card. The modal displays:

  • Statistics: Total quarantined sessions, permanent vs. expiring
  • Active Quarantine List: All currently quarantined sessions with details
  • Empty State: Confirmation when no sessions are blocked

Step 2: Add a Quarantine Entry ​

Click "Quarantine Session" to open the form:

Required Fields:

  • Session Identifier: The user identity to block. This should match how the user authenticates:

    • OAuth users: Their email address (e.g., user@example.com)
    • API keys: The key identifier (e.g., apikey:42)
    • IP-based: The client IP address

  • Reason: A description of why this session is being quarantined. This is recorded in the audit log and displayed to administrators.

Optional Fields:

  • Auto-expire: Check this to set a time-to-live (TTL) in minutes. The quarantine will automatically lift after the specified duration. If unchecked, the quarantine is permanent until manually released.

Step 3: Confirm ​

Click "Quarantine Session" to activate the block. The session is immediately quarantined — any in-flight requests from that session will be blocked on their next attempt.

What Happens to Quarantined Requests ​

When a quarantined session sends a request:

  1. The request is intercepted at the earliest point in the proxy pipeline (before content analysis, tool filtering, or upstream forwarding)
  2. The proxy returns HTTP 403 Forbidden with the message "Forbidden: session quarantined"
  3. A High severity security alert is generated with details including:
    • The session identifier
    • The quarantine reason
    • When the quarantine was established
  4. The alert is broadcast via WebSocket to the real-time dashboard
  5. The block is recorded in the audit log for compliance

Releasing Sessions ​

Release a Single Session ​

In the quarantine manager:

  1. Find the session in the active quarantine list
  2. Click the "Release" button next to it
  3. The session is immediately unblocked and can resume making requests

Release All Sessions ​

Click "Release All" to remove all quarantine entries for the proxy at once. A confirmation dialog prevents accidental release.

Automatic Release (TTL Expiry) ​

Sessions quarantined with a TTL automatically expire and are removed. A background process checks for expired entries every minute.

Accumulated Risk & Auto-Quarantine ​

The Session Quarantine system works in conjunction with the Session Risk Accumulator, which tracks cumulative risk per user session across multiple requests.

How Risk Accumulates ​

Each request is assigned a risk score by the policy engine (0-100). This score is added to the session's running total. Risk decays over time (halving every 30 minutes) to prevent normal low-risk activity from permanently accumulating.

Escalation Thresholds ​

Accumulated RiskActionDescription
100+WarnA Low severity alert is generated
200+Rate LimitA Medium severity alert flags the session for throttling
300+EscalateA High severity alert recommends human review
500+BlockThe session is automatically quarantined and a Critical alert is generated

Auto-Quarantine Behavior ​

When accumulated risk exceeds the Block threshold (500 by default):

  • The session is automatically added to the quarantine list with reason: "Auto-quarantined: accumulated risk exceeded block threshold"
  • The quarantine is permanent (no TTL) — it persists until an administrator reviews and releases it
  • A Critical severity alert is generated for immediate attention

This means a session that repeatedly sends suspicious requests (prompt injection attempts, tool abuse, policy violations) will be automatically contained without manual intervention.

API Reference ​

All endpoints require admin role authentication.

List Quarantined Sessions ​

GET /api/v1/proxies/{id}/quarantine

Response:

json
{
  "success": true,
  "data": {
    "proxy_id": 1,
    "sessions": [
      {
        "proxy_id": 1,
        "session_identifier": "user@example.com",
        "reason": "Repeated prompt injection attempts",
        "quarantined_at": "2026-03-19T14:30:00Z",
        "quarantined_by": "admin",
        "expires_at": null
      }
    ],
    "stats": {
      "total_quarantined": 1,
      "permanent": 1,
      "expiring": 0
    }
  }
}

Quarantine a Session ​

POST /api/v1/proxies/{id}/quarantine
Content-Type: application/json

{
  "session_identifier": "user@example.com",
  "reason": "Suspected compromised account",
  "ttl_minutes": 60
}

Release a Session ​

DELETE /api/v1/proxies/{id}/quarantine
Content-Type: application/json

{
  "session_identifier": "user@example.com"
}

Release All Sessions ​

DELETE /api/v1/proxies/{id}/quarantine/all

Best Practices ​

Incident Response ​

Immediate Containment:

  1. When a security alert indicates suspicious activity from a specific user or session, quarantine the session immediately
  2. Use a TTL (e.g., 60 minutes) if you expect to complete investigation quickly
  3. Use permanent quarantine for confirmed threats

Investigation:

  1. Review the quarantined session's recent request logs and alerts
  2. Check if the session identity corresponds to a legitimate user (potential account compromise) or an attacker
  3. Coordinate with the user's team if their account appears compromised

Resolution:

  1. Release the quarantine once the threat is mitigated (password reset, API key rotated, etc.)
  2. Document the incident in your security operations workflow
  3. Consider updating policies to prevent recurrence

Operational Guidelines ​

When to Quarantine:

  • Confirmed prompt injection or jailbreak activity
  • Suspected compromised API keys or OAuth tokens
  • Agent drift outside declared scope (AWARE: Actor Intent violation)
  • Data exfiltration attempts detected by DLP/redaction policies
  • Rate limit evasion or abuse patterns

When NOT to Quarantine:

  • Legitimate users experiencing application errors
  • Low-severity policy matches that are likely false positives
  • Performance issues (use rate limiting instead)
  • Blanket blocking of IP ranges (use network-level controls instead)

Monitoring Auto-Quarantine ​

  • Review the Alerts dashboard regularly for auto-quarantine events (Critical severity, rule ID: SESSION_RISK_ESCALATION)
  • Tune the risk thresholds if auto-quarantine is triggering too frequently on legitimate activity
  • Use the session risk stats endpoint to monitor accumulation patterns across your deployment

Troubleshooting ​

Common Issues ​

Session Not Being Blocked:

  • Verify the session identifier matches exactly how the user authenticates (OAuth email, API key format, or IP)
  • Check that the quarantine entry hasn't expired (if TTL was set)
  • Confirm the proxy is running — quarantine checks only apply to active proxies

Auto-Quarantine Triggering Too Often:

  • Review the risk scores being assigned to requests — high false-positive rates in policies inflate session risk
  • The default block threshold of 500 may need adjustment for high-traffic environments
  • Risk decay (30-minute half-life) should prevent accumulation from normal activity — if it doesn't, the base risk scores may be too high

Quarantine Not Persisting After Proxy Restart:

  • Quarantine entries are held in memory and do not persist across proxy restarts
  • For persistent blocking, consider disabling the user's OAuth session or revoking their API key
  • Future versions may add database persistence for quarantine entries

Releasing Doesn't Take Effect:

  • Release is immediate — if the user is still blocked, verify there isn't a second quarantine entry (e.g., both by email and by IP)
  • Check that the session identifier in the release request matches exactly (case-sensitive)
